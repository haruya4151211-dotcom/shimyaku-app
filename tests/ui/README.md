# UI テスト（Playwright）

史脈の画面を実際のブラウザで操作して確かめるテストです。MacBook Air と GitHub Codespaces（iPad Pro）で同じコマンド・同じ結果になるように作っています。

## 実行方法

| コマンド | 内容 |
|---|---|
| `npm run test:ui:install` | 初回だけ。テスト用の Chromium を入れる（Mac）。Codespaces では作成時に自動で入る |
| `npm run test:ui` | すべての UI テスト（PC 幅・スマホ 390 幅、@viewport の印のテストは 375・430 幅も）。Mac で約 30〜32 分 |
| `npm run test:ui:desktop` / `npm run test:ui:mobile` | PC 幅だけ／スマホ幅（390×844）だけ |
| `npm run test:ui:viewports` | 追加の画面幅（375×667・430×900）だけ。`@viewport` の印のテスト |
| `npm run test:ui:baseline` | データの回帰検知の基準を作り直す（カード・勢力・都市を**意図して**変えたときだけ。前の基準との違いを表示してから上書き） |
| `npm run test:ui:ux-pending` | 仕様未確定の UX 課題の記録（合否なし。通常の `test:ui` には含まれない） |
| `npx playwright test map-camera` | ファイル名の一部で絞り込む |
| `npx playwright test -g "リセット"` | テスト名で絞り込む |
| `npm run test:ui:perf` | 性能（本番ビルドを作って測る）。約 1 分 |
| `npm run test:ui:report` | 直前の結果を HTML で見る（失敗時のスクリーンショット・トレース付き） |

- 失敗が 1 件でもあれば終了コードは 1 になる。
- 開発サーバーはテストが自動で起動・終了する（ポート 5299。`UI_TEST_PORT` で変更可）。手元の `npm run dev` と同時に動かしてよい。
- テスト用サーバーはファイル監視と HMR を止めている（`tests/ui/vite.config.js`）。テストの実行中にファイルを保存しても影響しない
  （ただし保存した内容はその実行には反映されない）。
- 結果・スクリーンショット・トレースは `test-results/`（Git の管理外）。トレースは `npx playwright show-trace <trace.zip>` で開ける。

### Codespaces（iPad Pro）
1. Codespace を作る（`.devcontainer/devcontainer.json` により Node 26 と Chromium が入る）。
2. ターミナルで `npm run test:ui`。画面の表示は不要（ヘッドレス）。
3. 結果を見るときは `npm run test:ui:report` を実行し、転送されたポートをブラウザで開く。

### Mac
1. Node 26 系（`.nvmrc`）。`npm ci` のあと `npm run test:ui:install`。
2. `npm run test:ui`。普段使いの Chrome やそのプロフィールは使わない（Playwright の Chromium を使う）。
3. 通しで約 30〜32 分（Mac の実測）かかるので、途中でスリープすると時間の計測が狂って失敗する。`caffeinate -i npm run test:ui` で流すとよい
   （2026-11-16 に、開始直後のスリープで実行が 6 時間止まった）。

## データの保護
- テストごとに新しいブラウザ環境（使い捨てのプロフィール）を作るので、localStorage は毎回空から始まり、テスト間で混ざらない。
- 普段の Chrome、普段の開発サーバー（5173 番など）、利用者の学習の記録には一切触れない。

## 構成
| ファイル | 役割 |
|---|---|
| `playwright.config.js`（リポジトリ直下） | プロジェクト（desktop：1280×900・マウス／mobile：390×844・タッチ／mobile-375：375×667・mobile-430：430×900 は `@viewport` のテストだけ）、サーバーの自動起動 |
| `playwright.perf.config.js` | 性能の計測用（本番ビルド＋`vite preview`、新しいヘッドレス方式の Chromium） |
| `tests/ui/fixtures.js` | 全テスト共通：コンソールの警告・エラーの監視（1件でも失敗）、CDP セッション、操作部品 `ui` |
| `tests/ui/helpers/app.js` | 地図・シート・スライダーの操作と観測。**DOM のセレクタはここに集める** |
| `tests/ui/helpers/spec.js` | テストが前提にする仕様値（ズームの上限など）。`spec-sync.spec.js` が App.jsx の値と一致するか毎回確かめる |
| `tests/ui/helpers/plan.js` | 勢力・都市 → カードの検査計画を、いまのデータ（src/data）から組み立てる |
| `tests/ui/helpers/baseline.js`・`baseline/data-baseline.json`・`tools/update-baseline.mjs` | データの回帰検知（取り出し・差分／基準／基準の更新コマンド） |
| `tests/ui/vite.config.js` | テスト用の開発サーバー設定（アプリの設定＋監視・HMR 停止） |
| `tests/ui/ux-pending/` | 仕様未確定の UX 課題の記録（合否を持たない。判断が出たら通常のテストへ移す） |

| テスト | 確かめること |
|---|---|
| smoke | アプリが開き、地図が出る |
| spec-sync | 仕様値が App.jsx と一致（PC のみ） |
| map-camera | 各時代の初期表示・リセット、年代を変えてもカメラが動かない、拡大縮小の上限下限、ワールドラップ、ドラッグ後の誤タップ防止、ダブルクリック |
| map-regions | 地域移動ボタン |
| map-hit | 当たり判定：勢力の内側（押すと別の勢力が開く場所から 8px 以上離れた点）を押すとその勢力、小さな勢力も寄れば押せる、マウスは押した点の勢力。8px はテスト上の暫定基準（下の「基準値」を参照） |
| map-taps | 全年代の勢力・都市 → 詳細シート → カード数、海の勢力の航路（PC のみ。いまのデータどおりに動くか） |
| data-baseline | データが基準と一致するか（勢力ごとのカード数・都市・カードの所属。PC のみ。データが意図せず変わっていないか） |
| slider | 年代スライダーのキーボード操作（Tab でフォーカス、←→ で 10 年、両端で止まる。PC のみ） |
| sheet | 詳細シートのスワイプ・閉じる |
| search / search-warp | 検索モーダル、検索結果から地図への移動・強調・シート |
| territory-fade | 年代切り替えのクロスフェード |
| storage | 学習の記録の保存（localStorage が使えない環境も） |
| input | ctrl+ホイール、つまみ・地図のタッチ操作（ブラウザの警告なし） |
| perf/scrub-perf | 年代スライダーの高速ドラッグの性能（`test:ui:perf`） |
| ux-pending/boundary-touch | 記録のみ：境界ぎわのタッチが近くの小さな勢力へ寄せられる範囲（スマホ） |
| ux-pending/tap-size | 記録のみ：各画面幅の初期表示で、主な勢力の押せる点の余白（スマホ 3 幅） |

## テストを足す・直すとき
- 入力は**実際の入力イベント**で送る（`ui.press`・`ui.tapAt`・`ui.drag`・`ui.pinch`）。要素の `click()` を JavaScript で直接呼ぶと、
  地図の「ドラッグ直後のタップを止める」処理と食い違い、利用者の操作と違う結果になる。
  例外は「画面外の要素も含めた全件のデータの対応」を見る map-taps の `ui.openByLabel` だけ。
- 待つときは時間で待たず、状態を待つ（`expect.poll`・`ui.waitCameraStable`・`ui.waitMapSettled`）。
- 年代は `ui.moveToYear(年)`（スライダー下の年号チップを押す）。スライダー上の目盛りの点は近い年どうしが重なっていて、
  押すと隣の年が選ばれることがある。
- 期待値を変えるときは、App.jsx の仕様（行・定数）か開発ログの決定事項に結びつけて理由をコメントに書く。
  仕様値は `helpers/spec.js` に置く（変えると spec-sync が App.jsx との違いを知らせる）。
- 新しい勢力・都市・カードを足したときは、map-taps が自動で検査対象を増やす（計画はデータから作る）。
  一方 data-baseline は基準との違いとして失敗する。違いが意図どおりか確かめてから `npm run test:ui:baseline` で基準を更新し、
  基準のファイル（`tests/ui/baseline/data-baseline.json`）もデータの変更と一緒にコミットする。テストが基準を自動で書き換えることはない。
- 新しい画面・操作を足したときは、PC・スマホの両方で流れるテストを足す（スマホ専用・PC 専用なら `test.skip(ui.mobile, "理由")`）。
  画面の幅で結果が変わるもの（カメラ・初期表示・当たり判定・スライダー・シート・レイアウト）には `{ tag: "@viewport" }` を付け、
  375×667・430×900 でも流す。
- 仕様が決まっていない挙動は、期待値を作らず `ux-pending/` に記録用として置き、ユーザーの判断が出たら通常のテストへ移す。
- 失敗は skip や期待値の緩和で隠さない。アプリの不具合か、テストの不備か、環境かを分けて開発ログに残す。

## 基準値（2026-11-16、MacBook Air）
- 性能（本番ビルド、新しいヘッドレス方式）：PC 幅 p95 16.7ms、スマホ相当（CPU 4 倍遅く）p95 16.8ms。
- 所要時間：`npm run test:ui` 約 30〜32 分（全 4 プロジェクト・191 件、2026-11-16 の実測 2 回：30.6 分・31.7 分）。
- 結果：191 件中 成功 176・失敗 6・スキップ 9（スキップはすべて端末専用テストの対象外側）。
  電池切れのスリープは `caffeinate` でも防げない（2026-11-16 に電池 1% で実行が 10 時間止まった）。電源につないで流す。
- 既知の失敗 6 件（アプリ側の所見、ユーザーの判断待ち）：map-camera の 1939 年（390・375 幅）・1962 年（PC・390・375・430 幅）
  「初期表示でタップできる都市がある」。初期表示に都市が 1 つしか入らないため。期待値は緩めていない。
- 地図の当たり判定の余白（map-hit の 8px・map-camera の 10px）は**テスト上の暫定基準**で、UX 上の合格基準ではない。
  「押した点から、別の勢力が開く場所（または何も開かない場所）までの距離（半径）」を測っており、CLAUDE.md の「タップ範囲 40px 目安」
  （押せる部品の大きさ＝直径）とは別の指標。地図上の国をどれだけの大きさで押せるべきか（40px 目安を当てるか）は未確定で、
  ux-pending/tap-size に記録している（2026-11-16：1555 年のフランス王国の余白は 375 幅 8px・390 幅 12px・430 幅 14px）。
  - map-hit の 8px：当たり判定そのものの検査。タッチ位置の補正で隣の小さな勢力へ寄せられたのが 6px 以内だった（ux-pending/boundary-touch
    の実測）ので、それを超える最小の値にしている。狭い画面・引いた地図でも「内側を押せばその勢力」を厳密に確かめるため、必要以上に大きくしない。
  - map-camera の 10px：当たり判定の検査ではなく、各時代の初期表示で「勢力を押すとシートが開く」流れを確かめるときの、押す勢力の**選び方**。
    見えている面積の大きい勢力から、余白 10px 以上の点がある勢力を最大 3 つ選ぶ（合否は「1 つ以上押せる」）。大きな勢力だけを選べば足りるので、
    map-hit より余裕を持たせている。目的の違いによる意図した差で、どちらも期待値を緩めるためのものではない。
